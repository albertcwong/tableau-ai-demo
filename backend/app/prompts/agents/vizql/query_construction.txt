**🚨 CRITICAL: "How Many" / Count Queries - READ THIS! 🚨**

**WHEN USER ASKS "HOW MANY X" OR "COUNT OF X", YOU MUST ADD COUNTD FUNCTION!**

**COUNTD vs COUNT:**
- **COUNTD** = Count Distinct (counts unique values) - Use for "how many customers", "how many products", etc.
- **COUNT** = Count All (counts all rows including duplicates) - Use for "count of orders" when you want total order rows

**Patterns that REQUIRE COUNTD function (for distinct counts):**
- **"how many customers"** → `{"fieldCaption": "Customer Name", "function": "COUNTD"}`
- **"how many products"** → `{"fieldCaption": "Product Name", "function": "COUNTD"}`
- **"how many regions"** → `{"fieldCaption": "Region", "function": "COUNTD"}`
- **"count of distinct X"** → `{"fieldCaption": "X", "function": "COUNTD"}`
- **"number of unique X"** → `{"fieldCaption": "X", "function": "COUNTD"}`

**Patterns that REQUIRE COUNT function (for total rows):**
- **"count of orders"** → `{"fieldCaption": "Order ID", "function": "COUNT"}` (if you want total order rows)
- **"total number of rows"** → Use COUNT

**WRONG (missing COUNTD function):**
```json
{"fieldCaption": "Customer Name"}  // Missing function!
```

**CORRECT (with COUNTD function for distinct count):**
```json
{"fieldCaption": "Customer Name", "function": "COUNTD"}
```

**CRITICAL RULES:**
1. **ALWAYS add COUNTD function** when user asks "how many X" (for distinct entities like customers, products, regions)
2. Use COUNTD for counting unique/distinct values (customers, products, categories, etc.)
3. Use COUNT for counting total rows (orders, transactions, etc.)
4. Use the field name that represents the entity being counted (Customer Name, Order ID, Product Name, etc.)

6. For "how many customers", use Customer Name (or Customer) field with COUNTD

**🚨 CRITICAL: Date Dimension Functions - READ THIS FIRST! 🚨**

**WHEN USER REQUESTS TEMPORAL GROUPING, YOU MUST ADD A FUNCTION TO THE DATE FIELD!**

This is a **REQUIRED EXCEPTION** to the rule that dimensions don't have functions. Date dimensions NEED functions for temporal grouping!

**Temporal grouping keywords that REQUIRE date functions:**
- **"by month"** or **"monthly"** → **MUST use** `{"fieldCaption": "Order Date", "function": "TRUNC_MONTH"}`
- **"by year"** or **"yearly"** → **MUST use** `{"fieldCaption": "Order Date", "function": "TRUNC_YEAR"}`
- **"by quarter"** or **"quarterly"** → **MUST use** `{"fieldCaption": "Order Date", "function": "TRUNC_QUARTER"}`
- **"by week"** or **"weekly"** → **MUST use** `{"fieldCaption": "Order Date", "function": "TRUNC_WEEK"}`
- **"by day"** or **"daily"** → **MUST use** `{"fieldCaption": "Order Date", "function": "TRUNC_DAY"}`

**CRITICAL RULES:**
1. **ALWAYS use `function` field, NEVER use `calculation` field** for date truncation functions
2. **DO NOT** create formulas like `DATETRUNC('month',[Order Date])` - use `function: "TRUNC_MONTH"` instead
3. **DO NOT** assume pre-aggregated fields like "Month" or "Year" exist. Always apply the function to the raw date field (e.g., "Order Date", "Ship Date", "Date")
4. The `fieldCaption` must match the exact name of the date field in the schema (e.g., "Order Date")
5. **IF YOU OMIT THE FUNCTION, THE QUERY WILL RETURN DAY-LEVEL DATA INSTEAD OF MONTHLY/YEARLY AGGREGATES!**

**WRONG (returns day-level data, not monthly):**
```json
{"fieldCaption": "Order Date"}  // Missing function!
```

**CORRECT (returns monthly aggregates):**
```json
{"fieldCaption": "Order Date", "function": "TRUNC_MONTH"}
```

**WRONG (will cause error):**
```json
{"fieldCaption": "Order Date", "calculation": "DATETRUNC('month',[Order Date])"}
```

**CORRECT:**
```json
{"fieldCaption": "Order Date", "function": "TRUNC_MONTH"}
```

**Available Date Functions:**
- `TRUNC_YEAR`: Groups by year (e.g., 2024, 2023)
- `TRUNC_QUARTER`: Groups by quarter (e.g., Q1 2024, Q2 2024)
- `TRUNC_MONTH`: Groups by month (e.g., Jan 2024, Feb 2024)
- `TRUNC_WEEK`: Groups by week
- `TRUNC_DAY`: Groups by day
- `YEAR`: Extracts year number only
- `QUARTER`: Extracts quarter number only
- `MONTH`: Extracts month number only

**Prefer TRUNC_* functions** for grouping as they preserve full date context.

### 4. Filter Type Detection
Match user intent to filter types:

**SET Filter** - Specific values:
- "in ['North', 'South']", "equals", "is one of"
- Use when user specifies exact values to include/exclude

**MATCH Filter** - Substring matching:
- "contains 'phone'", "starts with 'A'", "ends with 's'"
- Use for fuzzy text matching

**DATE Filter** - Relative dates:
- "last 3 months" → periodType: "MONTHS", dateRangeType: "LASTN", rangeN: 3
- "this year" → dateRangeType: "CURRENT"
- "next quarter" → periodType: "QUARTERS", dateRangeType: "NEXT"
- Patterns: "last N {period}", "next N {period}", "this {period}", "to date"

**QUANTITATIVE_NUMERICAL Filter** - Range on aggregated fields (measures or aggregated dimensions):
- "at least 5", "greater than 1000", "more than X" → quantitativeFilterType: "MIN", min: X
- "at most 100", "less than 1000", "fewer than X" → quantitativeFilterType: "MAX", max: X
- "between 1000 and 5000" → quantitativeFilterType: "RANGE", min: 1000, max: 5000
- "only null values" → quantitativeFilterType: "ONLY_NULL" (no min/max)
- "only non-null values" → quantitativeFilterType: "ONLY_NON_NULL" (no min/max)
- Use for filtering aggregated measures (e.g., SUM(Sales) > 10000) or aggregated dimensions (e.g., COUNTD(State) >= 5)
- **CRITICAL**: The field in the filter MUST have a function (e.g., SUM, COUNTD, AVG) if filtering on aggregated values
- **Example**: "products sold in at least 5 states" → Filter on `{"fieldCaption": "State/Province", "function": "COUNTD"}` with MIN: 5

**QUANTITATIVE_DATE Filter** - Date ranges:
- "between 2024-01-01 and 2024-12-31" → quantitativeFilterType: "RANGE", minDate: "2024-01-01", maxDate: "2024-12-31"
- Use for specific date ranges (not relative dates)

## VizQL Rules (CRITICAL)
1. **MEASURES REQUIRE AGGREGATION**: If fieldRole is MEASURE, you MUST add "function" field
2. **USE EXACT fieldCaption**: Copy field names EXACTLY from schema (case-sensitive)
3. **DIMENSIONS AND AGGREGATION**: 
   - **DIMENSIONS CAN HAVE AGGREGATION FUNCTIONS**: The VDS API allows aggregation functions on dimension fields
   - Examples: `{"fieldCaption": "Customer Name", "function": "COUNT"}` is valid
   - Use aggregation functions on dimensions when user requests them (e.g., "count of customers", "count of orders")
   - **CRITICAL EXCEPTION: DATE DIMENSIONS**: If fieldRole is DIMENSION and dataType is DATE/DATETIME:
     - **IF user requests temporal grouping** ("by month", "by year", "monthly", "yearly", etc.):
       - **YOU MUST add `function` field** with appropriate TRUNC_* function (TRUNC_MONTH, TRUNC_YEAR, etc.)
       - Example: `{"fieldCaption": "Order Date", "function": "TRUNC_MONTH"}` for "by month"
       - **Without this function, queries return day-level data instead of monthly/yearly aggregates!**
     - **IF user does NOT request temporal grouping**: aggregation functions are optional (use if user requests aggregation)
   - **NUMERIC DIMENSIONS**: If fieldRole is DIMENSION but dataType is REAL or INTEGER, you CAN add "function" field
   - This handles cases where numeric fields (like "Sales") are categorized as dimensions in Tableau
   - When user asks for aggregation of a numeric dimension (e.g., "top sales by region"), use aggregation
4. **MATCH USER INTENT TO FIELD NAMES**: 
   - User says "sales" → Use "Total Sales" from schema (exact match)
   - User says "region" → Use "Region" from schema (exact match)
   - Never invent field names not in the schema
5. **USE DEFAULT AGGREGATIONS**: If a MEASURE field shows {default: SUM}, use SUM unless user specifies otherwise
6. **NUMERIC DIMENSIONS**: If a field is numeric (REAL, INTEGER) and user wants aggregation, use it even if marked as DIMENSION
7. **ALWAYS INCLUDE FIELDS**: Every query MUST have at least one field in query.fields array
8. **ONLY INCLUDE REQUESTED FIELDS**: 
   - If user asks for "sales", ONLY include Sales field (not Profit Ratio, not Profit, etc.)
   - If user asks for "total sales", ONLY include Sales field with SUM function
   - **CRITICAL**: Do NOT add calculated fields, ratios, or other fields unless user explicitly requests them
   - **CRITICAL**: Do NOT add fields just because they're in the Parsed Intent section - only add if user asked for them
   - If Parsed Intent shows calculations but user didn't mention "ratio", "margin", "calculate", etc., ignore them

**ALL filters MUST have the following required properties:**

1. **"filterType"** - REQUIRED for all filters (SET, MATCH, DATE, TOP, QUANTITATIVE_NUMERICAL, QUANTITATIVE_DATE, etc.)
2. **"field"** - REQUIRED for ALL filters (including QUANTITATIVE_NUMERICAL)
   - Must be an object: `{"fieldCaption": "FieldName"}`
   - Example: `"field": {"fieldCaption": "Region"}`
   - For QUANTITATIVE_NUMERICAL filters, the field MUST include a "function" property (e.g., SUM, COUNTD, AVG) because quantitative filters operate on aggregated values
   - Can filter on aggregated measures (e.g., SUM(Sales) > 10000) or aggregated dimensions (e.g., COUNTD(State) >= 5)

**CRITICAL: Use this decision tree to select the correct filter type:**

1. **IF user wants "top N" or "bottom N" dimension by measure:**
   → Use TOP filter (NOT sorting!)
   ```json
   {
     "field": {"fieldCaption": "DimensionName"},
     "filterType": "TOP",
     "howMany": N,
     "direction": "TOP|BOTTOM",
     "fieldToMeasure": {
       "fieldCaption": "MeasureName",
       "function": "SUM"
     }
   }
   ```

2. **IF user wants substring matching (contains/starts/ends with):**
   → Use MATCH filter
   ```json
   {
     "field": {"fieldCaption": "FieldName"},
     "filterType": "MATCH",
     "contains": "text",  // or "startsWith": "text", "endsWith": "text"
     "exclude": false
   }
   ```

3. **IF user wants relative dates (last/next N periods, this period):**
   → Use DATE filter
   ```json
   {
     "field": {"fieldCaption": "DateField"},
     "filterType": "DATE",
     "periodType": "DAYS|WEEKS|MONTHS|QUARTERS|YEARS",
     "dateRangeType": "LAST|LASTN|CURRENT|NEXT|NEXTN|TODATE",
     "rangeN": 3,  // Required for LASTN/NEXTN
     "anchorDate": "2024-01-01"  // Optional, defaults to today
   }
   ```

4. **IF user wants specific value inclusion/exclusion:**
   → Use SET filter
   ```json
   {
     "field": {"fieldCaption": "FieldName"},
     "filterType": "SET",
     "values": ["value1", "value2"],
     "exclude": false
   }
   ```

5. **IF user wants range on aggregated field (greater than, between, at least, at most):**
   → Use QUANTITATIVE_NUMERICAL filter
   - **For measures**: Filter on aggregated measure (e.g., SUM(Sales) > 10000)
   - **For aggregated dimensions**: Filter on COUNTD/COUNT/SUM of dimension (e.g., COUNTD(State) >= 5)
   - **quantitativeFilterType options:**
     - **MIN**: "at least X", "greater than X", "more than X" → min: X required
     - **MAX**: "at most X", "less than X", "fewer than X" → max: X required
     - **RANGE**: "between X and Y" → min: X, max: Y required
     - **ONLY_NULL**: "only null values" → no min/max
     - **ONLY_NON_NULL**: "only non-null values" → no min/max
   ```json
   {
     "field": {
       "fieldCaption": "MeasureName",
       "function": "SUM"  // REQUIRED if filtering on aggregated value
     },
     "filterType": "QUANTITATIVE_NUMERICAL",
     "quantitativeFilterType": "MIN|MAX|RANGE|ONLY_NULL|ONLY_NON_NULL",
     "min": 1000,  // Required for MIN or RANGE
     "max": 5000,  // Required for MAX or RANGE
     "includeNulls": false  // Optional, defaults to false
   }
   ```
   **Example**: "products sold in at least 5 states" → Filter on `{"fieldCaption": "State/Province", "function": "COUNTD"}` with MIN: 5

6. **IF user wants date range (between specific dates):**
   → Use QUANTITATIVE_DATE filter
   ```json
   {
     "field": {"fieldCaption": "DateField"},
     "filterType": "QUANTITATIVE_DATE",
     "quantitativeFilterType": "MIN|MAX|RANGE",
     "minDate": "2024-01-01",
     "maxDate": "2024-12-31"
   }
   ```

**Filter Priority Rules:**
- TOP filter takes precedence over sortPriority for "top N" queries
- DATE filter preferred over QUANTITATIVE_DATE for relative dates
- MATCH filter for fuzzy text matching, SET filter for exact matches

**QUANTITATIVE_NUMERICAL Filter Examples:**

A quantitative filter operates on a field with an aggregation. It can specify a minimum, maximum, or range of values. It can also be used to handle both null and non-null values.

**quantitativeFilterType Options:**
- **MIN**: The "min" value must be set. Use for "at least X", "greater than X", "more than X"
- **MAX**: The "max" value must be set. Use for "at most X", "less than X", "fewer than X"
- **RANGE**: Both "min" and "max" must be set. Use for "between X and Y"
- **ONLY_NULL**: Show only null values. Do NOT include "min" or "max" values.
- **ONLY_NON_NULL**: Show only non-null values. Do NOT include "min" or "max" values.

**Rules:**
- If quantitativeFilterType is ONLY_NULL or ONLY_NON_NULL, you CANNOT have "min" or "max" specified.
- If quantitativeFilterType is MIN, MAX, or RANGE, you can optionally set `includeNulls: true` (defaults to false) to include nulls.

**Example 1: Minimum value filter**
User: "show me total profit for products that have been sold in at least 5 different states"
```json
{
  "query": {
    "fields": [
      {"fieldCaption": "Product Name"},
      {"fieldCaption": "Profit", "function": "SUM"}
    ],
    "filters": [
      {
        "field": {
          "fieldCaption": "State/Province",
          "function": "COUNTD"
        },
        "filterType": "QUANTITATIVE_NUMERICAL",
        "quantitativeFilterType": "MIN",
        "min": 5
      }
    ]
  }
}
```

**Example 2: Range filter**
User: "customers with revenue between 10000 and 50000"
```json
"filters": [
  {
    "field": {
      "fieldCaption": "Sales",
      "function": "SUM"
    },
    "filterType": "QUANTITATIVE_NUMERICAL",
    "quantitativeFilterType": "RANGE",
    "min": 10000,
    "max": 50000
  }
]
```

**Example 3: Maximum value filter**
User: "products with sales less than 1000"
```json
"filters": [
  {
    "field": {
      "fieldCaption": "Sales",
      "function": "SUM"
    },
    "filterType": "QUANTITATIVE_NUMERICAL",
    "quantitativeFilterType": "MAX",
    "max": 1000
  }
]
```

**Example 4: Minimum with nulls included**
User: "products with sales at least 10000, including nulls"
```json
"filters": [
  {
    "field": {
      "fieldCaption": "Sales",
      "function": "SUM"
    },
    "filterType": "QUANTITATIVE_NUMERICAL",
    "quantitativeFilterType": "MIN",
    "min": 10000,
    "includeNulls": true
  }

```

## 🚨 CRITICAL: Context Filters for Hierarchical Dependencies

**WHEN TO USE CONTEXT FILTERS:**

Context filters establish a data scope that other filters operate within. Use `"context": true` when:

1. **Hierarchical Filter Dependencies** - One filter must be applied BEFORE another:
   - "given the top region, show me the top 3 customers"
   - "for the best category, what are the top products"
   - "within the largest market, find top sales reps"
   - "in Q1, show me the best performing stores"

2. **Pattern Recognition - Look for these linguistic cues:**
   - "given X, show Y" → X gets context:true
   - "for the [top/best] X, find Y" → X gets context:true
   - "within X, show Y" → X gets context:true
   - "in X, what are Y" → X gets context:true
   - Sequential filtering: "first X, then Y" → X gets context:true

3. **Logical Flow:**
   - First filter narrows the dataset (gets context:true)
   - Second filter operates on that narrowed dataset (no context)
   - Order matters! Context filters are applied first

**EXAMPLE 1: Hierarchical TOP filters**
User: "given the top region, give me the top 3 customers"

```json
"filters": [
  {
    "field": {"fieldCaption": "Region"},
    "filterType": "TOP",
    "howMany": 1,
    "direction": "TOP",
    "fieldToMeasure": {"fieldCaption": "Sales", "function": "SUM"},
    "context": true  // ← Applied FIRST to establish scope
  },
  {
    "field": {"fieldCaption": "Customer Name"},
    "filterType": "TOP",
    "howMany": 3,
    "direction": "TOP",
    "fieldToMeasure": {"fieldCaption": "Sales", "function": "SUM"}
    // ← Applied WITHIN the top region
  }
]
```

**EXAMPLE 2: Category scope with subcategory TOP**
User: "in the Furniture category, show me top 10 subcategories"

```json
"filters": [
  {
    "field": {"fieldCaption": "Category"},
    "filterType": "SET",
    "values": ["Furniture"],
    "exclude": false,
    "context": true  // ← Applied FIRST to narrow to Furniture
  },
  {
    "field": {"fieldCaption": "SubCategory"},
    "filterType": "TOP",
    "howMany": 10,
    "fieldToMeasure": {"fieldCaption": "Sales", "function": "SUM"},
    "direction": "TOP"
    // ← Applied WITHIN Furniture category
  }
]
```

**EXAMPLE 3: Date range with TOP filter**
User: "for Q1 2024, what were the top 5 products"

```json
"filters": [
  {
    "field": {"fieldCaption": "Order Date"},
    "filterType": "DATE",
    "periodType": "QUARTERS",
    "dateRangeType": "LASTN",
    "lastN": 1,
    "context": true  // ← Applied FIRST to establish Q1 scope
  },
  {
    "field": {"fieldCaption": "Product Name"},
    "filterType": "TOP",
    "howMany": 5,
    "fieldToMeasure": {"fieldCaption": "Sales", "function": "SUM"},
    "direction": "TOP"
    // ← Applied WITHIN Q1 data
  }
]
```

**WRONG vs CORRECT:**

❌ WRONG - Both filters at same level:
```json
// User: "given the top region, show top 3 customers"
"filters": [
  {"field": {"fieldCaption": "Region"}, "filterType": "TOP", "howMany": 1},
  {"field": {"fieldCaption": "Customer Name"}, "filterType": "TOP", "howMany": 3}
]
// Result: Top 3 customers ACROSS ALL regions, not within top region
```

✅ CORRECT - First filter as context:
```json
"filters": [
  {"field": {"fieldCaption": "Region"}, "filterType": "TOP", "howMany": 1, "context": true},
  {"field": {"fieldCaption": "Customer Name"}, "filterType": "TOP", "howMany": 3}
]
// Result: Top 3 customers WITHIN the top region
```

**RULES:**
- Only SET, TOP, and QUANTITATIVE filters can have context:true
- Apply context to the filter that establishes the broader scope
- Maximum one context filter per hierarchy level (but you can have multiple context filters total)
- If in doubt about hierarchy, ask yourself: "Which filter narrows the dataset for the other?"

## Calculations and Bins

**IMPORTANT: `calculation` vs `function`**
- Use `function` for built-in aggregations and date functions (SUM, AVG, TRUNC_MONTH, etc.)
- Use `calculation` ONLY for custom formulas that don't have a built-in function
- **NEVER use `calculation` for date truncation** - always use `function: "TRUNC_MONTH"` etc.

**🚨 CRITICAL: Aggregations Cannot Be Applied on Top of Aggregations 🚨**

**NEVER create nested aggregations! Aggregations cannot be applied on top of aggregations.**

**Rules:**
1. **No nested aggregations in calculations** - Do NOT create formulas like `AVG(SUM([Sales]))` or `COUNTD(SUM([Sales]))` where aggregations are nested directly
2. **No function field on aggregated calculations** - If a calculated field already contains aggregation (e.g., `SUM([Sales])` or `COUNTD(...)`), do NOT add a `"function"` field like `"function": "AVG"` or `"function": "COUNTD"`
3. **EXCEPTION: FIXED expressions return row-level data** - FIXED level-of-detail expressions return row-level data, so they CAN be aggregated:
   - ✅ VALID: `AVG({ FIXED [Order ID] : SUM([Sales]) })` - AVG aggregates the row-level results from FIXED
   - ✅ VALID: `{ FIXED : AVG( IF { FIXED [Order ID] : SUM([Profit]) } > 100 THEN { FIXED [Order ID] : SUM([Sales]) } END ) }` - Outer AVG aggregates FIXED results
   - ❌ INVALID: `COUNTD(IF { FIXED [Order ID] : SUM([Sales]) } > ... THEN [Order ID] END)` with `"function": "COUNTD"` - COUNTD appears twice (once in calculation, once as function)
4. **Check formulas before adding functions** - If a calculated field's formula contains SUM(), AVG(), COUNT(), COUNTD(), etc. OUTSIDE of FIXED expressions, it's already aggregated and cannot have a function field

**Examples of INVALID nested aggregations:**
- `AVG(SUM([Sales]))` ❌ - Direct nesting without FIXED
- `COUNTD(SUM([Sales]))` ❌ - Direct nesting without FIXED
- `SUM(AVG([Sales]))` ❌ - Direct nesting without FIXED

**Example of INVALID query (function on aggregated calculation):**
```json
{
  "fieldCaption": "Orders Above Avg Order Sales",
  "calculation": "COUNTD(IF { FIXED [Order ID] : SUM([Sales]) } > { FIXED : AVG({ FIXED [Order ID] : SUM([Sales]) }) } THEN [Order ID] END)",
  "function": "COUNTD"  // ❌ ERROR: Calculation already contains COUNTD outside FIXED, cannot add function
}
```
**Fix:** Remove the `"function": "COUNTD"` field since COUNTD is already in the calculation.

**Example of VALID query (FIXED returns row-level, can be aggregated):**
```json
{
  "fieldCaption": "Avg Order Value (Profit>100)",
  "calculation": "{ FIXED : AVG( IF { FIXED [Order ID] : SUM([Profit]) } > 100 THEN { FIXED [Order ID] : SUM([Sales]) } END ) }"
  // ✅ CORRECT: No function field needed, AVG aggregates FIXED results
}
```

**🚨 CRITICAL: Calculated Fields with Existing Aggregations 🚨**

**If a calculated field already contains aggregation functions in its formula, you MUST use it directly without adding a function field!**

**Rules:**
1. **Check the field's formula** - If the formula contains aggregation functions like SUM(), AVG(), COUNT(), etc., the field is already aggregated
2. **Do NOT add a function field** - For calculated fields that already have aggregation in their formula, you should reference the field directly without any `"function"` field
3. **Do NOT apply SUM, AVG, etc.** - Applying SUM, AVG, COUNT, or any other aggregation to an already-aggregated calculated field will cause an error
4. **Metadata API provides formulas** - The schema enrichment includes formulas from the Metadata API, which you can inspect to determine if a field already has aggregation

**How to detect aggregation in formulas:**
- Look for patterns like: `SUM([Field])`, `AVG([Field])`, `COUNT([Field])`, `COUNTD([Field])`, etc.
- If you see these patterns in the formula, the field is already aggregated

**WRONG (trying to aggregate an already-aggregated field):**
```json
{
  "fieldCaption": "Profit Ratio",
  "function": "SUM"  // ❌ ERROR: Field formula already contains aggregation - remove function!
}
```

**CORRECT (using field directly without function):**
```json
{
  "fieldCaption": "Profit Ratio"  // ✅ CORRECT: Field already has aggregation in formula, use directly
}
```

**Example:**
If "Profit Ratio" has formula `SUM([Profit])/SUM([Sales])`, use it like:
```json
{
  "fieldCaption": "Profit Ratio"
}
```

**NOT like:**
```json
{
  "fieldCaption": "Profit Ratio",
  "function": "SUM"  // ❌ WRONG - field already aggregated!
}
```

**🚨 CRITICAL: Calculated Field Names Must Be Unique 🚨**

**When creating a calculated field, the `fieldCaption` MUST NOT match any existing field name in the schema!**

**Rules:**
1. **Check the schema** - Before naming a calculated field, verify the name doesn't exist
2. **Use descriptive, unique names** - Add prefixes/suffixes to make it clear it's a calculation:
   - ✅ Good: "Profit Margin", "Sales Ratio", "Avg Price Per Unit", "Total Revenue Calculated"
   - ❌ Bad: "Sales" (if "Sales" already exists), "Profit" (if "Profit" already exists)
3. **Common patterns for calculated fields:**
   - Add "Ratio", "Margin", "Rate", "Per", "Calculated", "Computed" to the name
   - Example: If "Sales" exists, use "Sales Ratio" or "Sales Margin" instead
4. **Case-insensitive matching** - "Sales" and "sales" are considered the same name

**WRONG (conflicts with existing field):**
```json
"fields": [
  {
    "fieldCaption": "Sales",  // ❌ ERROR: "Sales" already exists in schema!
    "calculation": "SUM([Profit])/SUM([Sales])"
  }
]
```

**CORRECT (unique name):**
```json
"fields": [
  {
    "fieldCaption": "Profit Margin",  // ✅ Unique name, doesn't conflict
    "calculation": "SUM([Profit])/SUM([Sales])"
  }
]
```

**Ad-hoc Calculation Example (custom formula):**
```json
"fields": [
  {
    "fieldCaption": "Profit Margin",
    "calculation": "SUM([Profit])/SUM([Sales])"
  }
]
```

**Parameter in Calculation:**
```json
"fields": [
  {
    "fieldCaption": "Binned Profit",
    "calculation": "INT([Profit] / [Profit Bin Size]) * [Profit Bin Size]"
  }
],
"parameters": [
  {
    "parameterCaption": "Profit Bin Size",
    "value": 50
  }
]
```

**Create Bin Example:**

## Sorting Rules

**When to use sorting vs TOP filter:**
- Use TOP filter for "top N" or "bottom N" queries
- Use sortPriority for general sorting without limiting results
- Cannot have duplicate sort priorities
- Lower sortPriority number = higher priority (sorted first)

**Sorting Example:**
```json
"fields": [

    "fieldCaption": "Category",
    "sortPriority": 1,
    "sortDirection": "ASC"
  },

    "sortPriority": 2,
    "sortDirection": "DESC"
  }
]
```

## Step-by-Step Query Building Process

**Step 1: Identify Required Fields**
- Extract measures mentioned: "sales", "revenue", "profit", "total", "count"
- Extract dimensions mentioned: "by region", "per category", "for each customer"
- **CHECK FOR TEMPORAL GROUPING**: Look for keywords "by month", "by year", "monthly", "yearly", "by quarter", "by week", "by day"
  - If found, you MUST add a date function (TRUNC_MONTH, TRUNC_YEAR, etc.) to the date field!
  - Example: User says "sales by month" → Include `{"fieldCaption": "Order Date", "function": "TRUNC_MONTH"}`
- **CRITICAL**: If user says "total sales", you MUST include a Sales field with SUM function
- **CRITICAL**: If user says "sales by region", you MUST include BOTH Region and Sales fields

**Step 2: Determine Aggregation Functions**
- "total", "sum" → Use SUM function
- "average", "avg" → Use AVG function
- "count" → Use COUNT function
- "maximum", "max" → Use MAX function
- "minimum", "min" → Use MIN function
- If no aggregation specified for a measure, use SUM (default)

**Step 3: Detect Filters Needed**
- Top N pattern? → Use TOP filter (NOT sorting!)
- Date filter? → Use DATE or QUANTITATIVE_DATE filter
- Text matching? → Use MATCH filter
- Specific values? → Use SET filter
- Range on measure? → Use QUANTITATIVE_NUMERICAL filter

**Step 4: Build Query Structure**
- Start with required fields in query.fields array
- Add filters if needed
- Ensure datasource and options are present
